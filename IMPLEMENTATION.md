# Реализация сервиса генерации карточек товаров

## Сопроводительное сообщение

Реализован демонстрационный сервис на Python/FastAPI, который принимает данные товара
в JSON, отправляет их в LLM через API и возвращает черновик карточки товара в JSON или
Markdown. Поддерживаются локальная Ollama, OpenAI и Anthropic. Ответ модели проверяется
по требованиям ТЗ, при нарушениях выполняются повторные попытки, а затем безопасная
нормализация. Технические значения, которых нет во входных данных, не попадают в результат.

## Что реализовано

- REST API на FastAPI:
  - `POST /generate` — карточка одного товара в JSON;
  - `POST /generate/batch` — несколько товаров параллельно;
  - `POST /generate/markdown` — карточка в Markdown;
  - `GET /health` — состояние сервиса и доступные провайдеры.
- Единый LLM-клиент: Ollama, OpenAI, Anthropic.
- Настройки через `.env`, API-ключи не хранятся в коде и исключены из Git.
- Валидация входных данных через Pydantic: пустые `name` и `manufacturer` отклоняются.
- Проверка результата:
  - `seo_title` — до 70 символов;
  - `seo_description` — 800–1200 символов;
  - `search_queries` — 3–5 штук;
  - `commercial_block` — не пустой;
  - отсутствие технических значений, которых не было во входных данных.
- До 3 попыток генерации с передачей модели списка нарушений.
- Детерминированная нормализация, если модель так и не уложилась в лимиты.
- Защита от выдуманных характеристик: значения сверяются с входными данными,
  неизвестные характеристики получают значение `данных нет` и попадают в `missing_fields`.
- Понятное сопоставление ошибок: `422`, `502`, `503`, `500`.
- Русские docstring'и, логи и тексты ошибок.
- `black` и `flake8` проходят без ошибок.
- `Dockerfile`, `docker-compose.yml` с Ollama и `.dockerignore` для контейнерного запуска.

## Принятые решения

1. **FastAPI + Pydantic** — быстрый старт, автоматическая валидация, Swagger из коробки.
2. **OpenAI SDK для Ollama** — Ollama предоставляет OpenAI-совместимый endpoint `/v1`,
   поэтому отдельный SDK не нужен.
3. **Единый `UnifiedLLMClient`** — провайдер определяется по имени модели, а не жёстко
   задаётся в коде. Это позволяет переключаться через `.env`.
4. **Проверка и нормализация отдельно от генерации** — сервис генерации не смешивается
   с правилами ТЗ; проверки вынесены в `src/utils/product_card.py`.
5. **Повторная генерация с обратной связью** — модель получает список конкретных
   нарушений, а не просто повторный запрос.
6. **Детерминированная нормализация** — если модель несколько раз не смогла достичь
   нужной длины, текст добирается только фактами из входных данных, без «выдумывания».
7. **Явные доменные исключения** — сетевые ошибки и ошибки API не превращаются в
   неинформативный `500`.

## С какими сложностями столкнулись

- Ollama возвращала `404`: модель по умолчанию подставлялась из `DEFAULT_PROVIDER`
  (`ollama`) вместо `DEFAULT_MODEL`. Исправлено.
- Небольшая модель `llama3.2` стабильно генерировала SEO-описание короче 800 символов.
  Решение: несколько попыток с указанием нарушений + детерминированный добор текста
  из входных данных.
- Модель иногда искажала значения характеристик или добавляла лишние поля.
  Решение: сверка `key_specs` с входными данными и замена неизвестных значений на
  `данных нет`.
- Логи `loguru` были написаны в стиле `%s`, из-за чего сообщения выводились с
  плейсхолдерами. Формат исправлен на `{}`.
- В задании упоминались два товара, но в переписке и проекте был только JSON манометра
  DM 02. Второй товар ниже помечен как демонстрационный.

## Промпты и принятые решения

Системный промпт (`src/services/prompts.py`) задаёт жёсткие правила:

- использовать только данные из запроса;
- не добавлять характеристики «из общих знаний»;
- отсутствующие значения помечать как `данных нет` и добавлять поле в `missing_fields`;
- возвращать только валидный JSON без Markdown-обёрток;
- соблюдать лимиты: заголовок до 70 символов, описание 800–1200 символов,
  3–5 поисковых запросов, коммерческий блок на 2–3 предложения.

Пользовательский промпт передаёт название, производителя, характеристики и описание.
При повторной попытке к нему добавляется сообщение со списком конкретных нарушений.
Так модель получает обратную связь и исправляет результат точечно, а не генерирует
всё заново «вслепую».

Дополнительно код, а не только промпт, проверяет ограничения. Это важно: текстовые
инструкции модель может проигнорировать, а валидатор и нормализация гарантируют
соблюдение требований.

## Ограничения решения и возможные улучшения

Ограничения:

- Качество карточек зависит от модели. Небольшие локальные модели могут давать
  повторы или слишком короткий текст.
- Fallback-нормализация может делать описание шаблонным и повторяющимся.
- Нет авторизации, ограничения частоты запросов и сохранения истории.
- Нет кэширования ответов и очереди задач для больших batch-запросов.
- Нет автоматических тестов.

Возможные улучшения:

- Добавить unit/integration-тесты (pytest) для валидации, нормализации и маппинга ошибок.
- Использовать structured output / JSON Schema там, где провайдер это поддерживает.
- Сделать простую веб-форму для ручного ввода товара.
- Добавить GPU-профиль для Ollama в `docker-compose.yml`.
- Добавить метрики, structured logging и health-check с реальной проверкой провайдера.
- Кэшировать результаты по хэшу входных данных.
